2 Exceptions

Scala supporte les exceptions de manière semblable à Java. La différence principale est qu’en Scala, toutes les exceptions sont unchecked. Cela signifie que le compilateur n’oblige pas à intercepter ou à déclarer les “checked” exception dans les signatures de méthodes.

En Scala, nous utiliserons plutôt les types Option et Either pour gérer nos erreurs métier. Nous éviterons de lancer des exceptions dans notre propre code. Les exceptions seront utilisées dans ces cas :

  • utilisation d’une bibliothèque Java qui lance des exceptions
  • utilisation de certaines fonctions du SDK qui peuvent lancer des exceptions

Nous verrons plus loin comment encapsuler les exceptions dans Try, et pourquoi les exceptions sont à éviter en programmation fonctionnelle.

2.1 throw

// En Java, cette exception serait "checked", car elle hérite d'Exception 
// En Java, les exceptions "unchecked" héritent de RuntimeException ou Error
class MinorException(s: String) extends Exception(s)

case class Person(name: String, age: Int)

// pas de déclaration throws, MinorException est unchecked
def validateAge(ageStr: String) : Int = 
  val age = ageStr.toInt // peut lancer NumberFormatException
  if (age < 18)
    throw new MinorException("Age must be >= 18")

2.2 try/catch/finally

  • Vous pouvez utiliser try, catch, finally comme en Java.
  • la différence est que le block catch utilise le pattern matching, avec des case pour chaque exception
    • On peut utiliser NonFatal(e) pour intercepter les exceptions qui ne sont pas “fatales” pour l’application.
    • Les exceptions fatales sont par exemple les OutOfMemoryError, StackOverflowError, … (voir le source de scala.util.control.NonFatal)
/** @return "ok" ou un message d'erreur */
def validatePerson(name: String, age: String): String =
  try
    age = validateAge(ageStr)
    "ok"
  catch
    case e: MinorException => e.getMessage
    case e: (IllegalArgumentException | NumberFormatException) => e.getMessage
    case NonFatal(e) =>
      logger.error("Not too bad", e)
      e.getMessage
  finally
    println("ce code s'exécute même si une exception n'est pas interceptée")
Tip

Vous pouvez annoter une méthode avec @throws[MinorException] pour documenter quelles exceptions peuvent être lancées. Le compilateur Scala n’en tiendra pas compte pour valider votre code Scala.

Cependant, le byte-code généré aura une clause throws MinorException. Cela peut être utile si votre code est appelé depuis Java.

3 Le type Option

Le type Option est un ADT qui permet de représenter “une valeur ou rien”. On peut aussi le voir comme une Seq qui contient 0 ou 1 élément. Il est utilisé lorsqu’une fonction renvoie un résultat qui peut ne pas exister, et remplace l’utilisation de null.

Important

En Scala, nous n’utiliserons jamais null, à part pour appeler des bibliothèques Java. Voir un null dans du code Scala devrait immédiatement attirer la suspicion et les foudres du reviewer !

3.1 Option - Exemple d’utilisation

val myList = List(1, 2, 3)
val head: Option[Int] = liste.headOption // Some(1)

val myList2 = List.empty
val head2: Option[Int] = liste.headOption // None

val nameToAge = Map("alice" -> 18, "bob" -> 17)
val name1 = "bob"
val optAge: Option[Int] = nameToAge.get(name1) // Some(17)

val name2 = "charles"
val optAge2: Option[Int] = nameToAge.get(name2) // None

Pour récupérer la valeur, nous utiliserons le pattern matching, ou getOrElse :

optAge match
  case Some(age) => age
  case None => -1
  
// équivalent
optAge.getOrElse(-1)
Important

Il existe une méthode Option.get qui lance une NoSuchElementException lorsque l’option est un None.

Il ne faut pas l’utiliser. Cela équivaut à utiliser un null et risquer des NullPointerException. L’objectif du type Option est justement d’éviter ces exceptions.

3.2 Option - Remplacer une exception

Nous pouvons l’utiliser pour remplacer une gestion d’exception. L’inconvénient est que nous perdons le message d’erreur de l’exception :

def parseAge(age: String): Option[Int] =
  try
    Some(age.toInt)
  catch
    case e: NumberFormatException => None

parseAge("toto") // None 
parseAge("18")   // Some(18)

Lorsque parseAge renvoie None, nous savons qu’il y a eu un problème, mais nous n’avons pas de message d’erreur.

Nous pouvons également modifier notre autre méthode checkAge pour utiliser Option au lieu de lancer une exception :

def checkAge(age: Int) : Option[Int] =
  if (age < 18) 
    None 
  else 
    Some(age)

Pour combiner des méthodes qui renvoient une Option, nous pouvons utiliser le pattern matching :

case class Person(name: String, age: Int)

def checkName(name: String): Option[String] =
  if (name.isEmpty) None else Some(name)

def validatePerson(name: String, ageStr: String): Option[Person] =
  checkName(name) match
    case Some(checkedName) =>
      parseAge(ageStr) match
        case Some(age) =>
          checkAge(age) match
            case Some(checkedAge) => Some(Person(checkedName, checkedAge))
            case None => None
        case None => None
    case None => None

3.3 Option - combiner avec map et flatMap

Cette approche est peu lisible. Nous pouvons simplifier ce code en utilisant map et flatMap. Le type Option peut en effet être considéré comme une Seq contenant 0 ou 1 élément. Il possède beaucoup de méthodes communes avec Seq.

def validatePerson2(name: String, ageStr: String): Option[Person] =
  checkName(name)
    .flatMap(checkedName => 
      parseAge(ageStr)
        .flatMap(age => checkAge(age)) 
        .map(checkedAge => Person(checkedName, checkedAge))
    )

C’est un peu plus concis, mais pas encore très lisible !

Dans le CM3, nous avions vu que le for/yield de Scala est un “sucre syntaxique” qui permet de remplacer map et flatMap. Nous pouvons donc l’utiliser pour simplifier encore notre code !

def validatePerson3(name: String, ageStr: String): Option[Person] = 
  for 
    checkedName <- checkName(name)
    age <- parseAge(ageStr)
    checkedAge <- checkAge(age)
  yield
    Person(checkedName, checkedAge)

4 Le type Either

Option nous permettait de signaler qu’il y avait eu un problème pour produire une valeur. Mais il ne nous permettait pas d’avoir d’informations sur le problème.

Either résout ce problème avec cette convention :

  • Right signifie que tout c’est bien passé (it’s all right !)
  • Left signifie qu’il y a eu un problème, et stocke une valeur représentant le problème.

Either[A, B] signifie “j’ai soit un résultat (Right) de type B, soit une erreur (Left) de type A”.

4.1 Either - Exemple

Reprenons nos méthodes précédentes pour utiliser Either :

def parseAge(ageStr: String): Either[String, Int] =
  try
    Right(ageStr.toInt)
  catch
    case e: NumberFormatException => Left(s"$ageStr is not an int")


def checkAge(age: Int) : Either[String, Int] =
  if (age < 18)
    Left(s"$age must be >= 18")
  else
    Right(age)


def checkName(name: String): Either[String, String] =
  if (name.isEmpty) Left("name is required") else Right(name)

Le type Either est “right-biased”. Cela signifie que lorsqu’on appelle map ou flatMap, cela transforme les instances Right, et laisse les Left inchangés. Comme Either implémente map et flatMap, nous pouvons réutiliser validatePerson quasiment inchangé ! Nous avons juste à changer le type de retour :

def validatePerson(name: String, ageStr: String): Either[String, Person] =
  for
    checkedName <- checkName(name)
    age <- parseAge(ageStr)
    checkedAge <- checkAge(age)
  yield
    Person(checkedName, checkedAge)

Exemple d’utilisation :

validatePerson("", "17")
// Left(name is required)

validatePerson("John", "abc")
// Left(abc is not an int)

validatePerson("John", "17")
// Left(17 must be >= 18)

validatePerson("John", "20")
// Right(Person(John,20))

4.2 Either - modélisation des erreurs

Dans notre exemple, nous avions utilisé String comme type erreur dans Either[String, A]. Cela permet d’avoir un message sous forme de chaîne de caractères. Cela peut être suffisant pour afficher un message dans un programme simple.

Cependant, cette approche est souvent insuffisante en production :

  • les messages d’erreurs sont couplés avec le code qui produit l’erreur
    • les messages sont répartis partout dans le code.
    • difficile d’offrir d’autres langues
  • les appelants ne peuvent pas traiter une erreur particulière

Il est plus pratique d’avoir des types structurés pour pouvoir réagir différemment en fonction du type d’erreur, et pour pouvoir conserver plus d’informations sur l’erreur. En Java, nous utilisions des exceptions personnalisées. Avec Either, nous pouvons créer nos propres ADT pour modéliser nos erreurs :

sealed trait PersonError:
  def message: String

case class PersonIntFieldParsingError(field: String, value: String) extends PersonError:
  override def message: String = s"$field with value: $value is not an integer"

case object PersonAgeMinorError extends PersonError:
  override def message: String = s"age must be >= 18"

case class PersonFieldRequiredError(field: String) extends PersonError:
  override def message: String = s"$field is required"

Nos messages d’erreur sont maintenant centralisés. Nos fonctions de validation peuvent renvoyer un type qui indique clairement à l’appelant le problème qui peut se produire :

def parseAge(ageStr: String): Either[PersonIntFieldParsingError, Int] =
  try
    Right(ageStr.toInt)
  catch
    case e: NumberFormatException => Left(PersonIntFieldParsingError("age", ageStr))


def checkAge(age: Int) : Either[PersonAgeMinorError.type, Int] =
  if (age < 18)
    Left(PersonAgeMinorError)
  else
    Right(age)


def checkName(name: String): Either[PersonFieldRequiredError, String] =
  if (name.isEmpty)
    Left(PersonFieldRequiredError("name"))
  else
    Right(name)

Lorsqu’on combine les fonctions de validations, on peut traiter toutes les erreurs en utilisant le trait PersonError :

def validatePerson(name: String, ageStr: String): Either[PersonError, Person] =
  for
    checkedName <- checkName(name)
    age <- parseAge(ageStr)
    checkedAge <- checkAge(age)
  yield
    Person(checkedName, checkedAge)

5 Le type Try

Le type Try permet d’encapsuler les méthodes qui lancent des exceptions. Sa structure ressemble à un Either où le type de gauche serait toujours de type Throwable.

5.1 Constructeur

La définition de Try.apply prend une fonction en paramètre “by-name” avec r: => T. Cela signifie que la fonction r ne sera évaluée que lorsqu’on l’appelle.

Try:
  def apply[T](r: => T): Try[T] =
    try
      val r1 = r
      Success(r1)
    catch
      case NonFatal(e) => Failure(e)

5.2 Utilisation

import scala.util.Try 

def parseAgeTry(ageStr: String): Try[Int] =
  Try(ageStr.toInt)

parseAgeTry("abc")
// Failure(java.lang.NumberFormatException: For input string: "abc")
parseAgeTry("18")
// Success(18)

Si l’on souhaite conserver notre définition qui renvoyait un Either, on peut utiliser .toEither :

def parseAge(ageStr: String): Either[PersonIntFieldParsingError, Int] =
  Try(ageStr.toInt)
    .toEither
    .left // on souhaite transformer la partie gauche
    .map(exception => PersonIntFieldParsingError("age", ageStr))

6 Le type Validation

Le type Either a un inconvénient : il ne permet pas de connaître la liste des erreurs qui se sont produites. L’enchaînement des vérifications avec flatMap se termine dès qu’il y a une erreur.

Dans notre méthode validatePerson, on souhaiterait idéalement valider le nom et l’age séparément. Si à la fois le nom et l’age ne sont pas validés, on aimerait avoir les deux messages d’erreur.

La bibliothèque ZIO Prelude possède un type Validation qui permet de résoudre ce problème :

import zio.prelude.Validation

import zio.prelude.Validation

def checkName(name: String): Validation[PersonFieldRequiredError, String] =
  if (name.isEmpty)
    Validation.fail(PersonFieldRequiredError("name"))
  else
    Validation.succeed(name)

def parseAge(ageStr: String): Validation[PersonIntFieldParsingError, Int] =
  Validation(ageStr.toInt).mapError(_ => PersonIntFieldParsingError("age", ageStr))

def checkAge(age: Int): Validation[PersonAgeMinorError.type, Int] =
  if (age < 18) 
    Validation.fail(PersonAgeMinorError)
  else 
    Validation.succeed(age)

// map/flatMap enchaîne les validations à la suite
def validateAgeString(ageStr: String): Validation[PersonError, Int] =
  for
    age <- parseAge(ageStr)
    checkedAge <- checkAge(age)
  yield checkedAge

// validateWith combine deux validations indépendantes 
def validatePerson(name: String, ageStr: String): Validation[PersonError, Person] =
  Validation.validateWith(checkName(name), validateAgeString(ageStr))(Person.apply)

La liste d’erreurs peut être obtenue avec :

validatePerson("", "17") match
  case Validation.Failure(_, errors) => errors.foreach(err => println(err.message))
  case Validation.Success(_, p) => println(p)

/*
name is required
age must be >= 18  
*/

7 Bonnes pratiques

En Scala, les exceptions sont plutôt à réserver lorsqu’on appelle du code Java ou lorsqu’on appelle certaines fonctions du SDK qui malheureusement lancent des exceptions.

Tip

Bonnes pratiques de gestion des erreurs en Scala :

  • éviter de lancer des exceptions
  • laisser remonter les exceptions “fatales”
  • encapsuler les exceptions “recoverable” avec Try ou Either
  • éviter les fonctions du SDK qui lancent des exceptions, comme Option.get
  • utiliser Option, Either ou Validated pour gérer les erreurs métier
  • utiliser des ADT pour modéliser les erreurs métier
  • éviter les blocs try/catch/finally, sauf pour appeler du code Java

En programmation fonctionnelle, les exceptions sont à éviter car :

  • elles ne sont pas reflétées dans les signatures de méthodes
    • les appelants ne savent pas quelles erreurs peuvent se produire
  • elles cassent la transparence référentielle (nous reparlerons de ce concept au CM6).
  • le code de gestion d’exceptions n’est pas composable avec map, flatMap

A contrario, les types fonctionnels Option, Either, Validated :

  • sont visibles dans les signatures
  • obligent à traiter tous les cas d’erreur
  • sont composables
