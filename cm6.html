2 Transparence référentielle

Important

On dit qu’une expression est référentiellement transparente lorsqu’elle peut être remplacée par sa valeur sans changer le comportement du programme, et ceci dans tous les contextes.

Une fonction qui garantit cette propriété est une fonction pure : la valeur de retour dépend uniquement des arguments passés à la fonction.

Exemple de fonction pure :

def pureSquare(x: Int): Int = x * x
val pureExpr = pureSquare(4) + pureSquare(3)
// on pourrait remplacer l'appel à pureSquare par son résultat sans changer le comportement
val pureExpr2 = 16 + 9

Exemple de fonction impure :

var globalState = 1
def impure(x: Int): Int = 
  globalState = globalState + x
  globalState
}
val impureExpr = impure(3) + impure(3)
// Si je remplace impure(3) par sa valeur de retour initiale 4, le comportement change
val impureExpr2 = 4 + 4 // impureExpr2 != impureExpr

2.1 Effets de bords

Toute fonction qui a des effets de bord (side effect) est impure. Un effet de bord peut être :

  • Modifier une variable se trouvant en dehors de la fonction
  • Afficher sur la console
  • Ouvrir une connection réseau
  • Lire/Écrire dans un fichier, une base de données
  • De manière générale, toute interaction avec le monde extérieur.

2.2 Exceptions et transparence référentielle

En programmation fonctionnelle, nous évitons d’utiliser les exceptions, car leur utilisation casse la transparence référentielle :

def area(width: Int, height: Int): Double =
  if (width > 5 || height > 5)
    throw new IllegalArgumentException("too big")
  else
    width * height

Ce code :

val total =
  try
    area(3, 2) + area(6, 2)
  catch
    case e: IllegalArgumentException => 0

N’est pas équivalent à celui-ci :

var area1 = area(3, 2)
val area2 = area(6, 2)

val total2 =
  try
    area1 + area2
  catch
    case e: IllegalArgumentException => 0

Si une fonction lance une exception, on ne peut pas toujours remplacer l’appel d’une fonction par son résultat. Nous n’avons pas ce problème lorsque nous utilisons des structures Either ou Validated.

2.3 Avantages des fonctions pures

La transparence référentielle est un concept clé en programmation fonctionnelle. Si la majorité du code de votre programme est composé de fonctions pures, il devient beaucoup plus facile de :

  1. Comprendre ce que fait le programme. Si on voit un appel de fonction, on sait que la valeur de retour dépend uniquement des arguments. Pas besoin de tenir compte de l’état d’un attribut, ou de risquer d’avoir des modifications d’attributs dans les arguments.
  2. Refactoriser. On peut utiliser le refactoring “introduce variable” sans se soucier de la position de la variable dans le code.
  3. Tester ses fonctions. On a juste à passer différents arguments et tester la valeur de retour.
  4. Écrire des programmes multithreads. Plusieurs appels de fonctions pures peuvent être exécutés en parallèle. Pas de risque de modification concurrente de la même variable.

3 given / using

Le mot clé given permet de déclarer un objet qui sera automatiquement passé comme argument d’une fonction utilisant using :

case class ServerConfig(host: String, port: Int)

given ServerConfig("localhost", 8080)

// ...
def callGet(url: String)(using cfg: ServerConfig): String =
  val socket = new Socket(cfg.host, cfg.port)
  // ...
  response

// Lorsqu'on appelle la fonction, pas besoin de passer cfg
// si on a une instance "given" du même type dans notre scope  
callGet("/customers")

3.1 Cas d’utilisation : Tri

Nous souhaitons trier une liste d’objets Person en fonction d’un attribut surname. Dans notre programme, nous souhaitons offrir un tri “standard”, mais laisser la possibilité à l’appelant de passer un ordre de tri personnalisé.

case class Person(surname: String, name: String, age: Int)

En Java, nous aurions créé une classe qui implémente Comparator<Person>. En Scala, nous devons déclarer une instance de Ordering[Person] :

object Person:
  val defaultPersonOrdering: Ordering[Person] = new Ordering[Person] {
    override def compare(x: Person, y: Person): Int =
      x.surname.compareTo(y.surname)
  }

L’inconvénient est qu’il faut passer cet objet Ordering partout où on a besoin de comparer des Person. :

def listPeople(persons: Seq[Person])
              (ordering: Ordering[Person]) = persons.sorted(ordering)

def someOtherMethodRequiringOrdering(alice: Person, bob: Person)
                                    (ordering: Ordering[Person]) = ???

def yetAnotherMethodRequiringOrdering(persons: List[Person])
                                     (ordering: Ordering[Person]) = ???

Pour appeler ces méthodes, nous devons retrouver l’instance Ordering “standard” et la passer en argument, ce qui peut rapidement devenir répétitif.

En utilisant given et using, nous pouvons déléguer cette tâche ingrate au compilateur :

object Person: 
  given defaultPersonOrdering: Ordering[Person] = new Ordering[Person] {
    override def compare(x: Person, y: Person): Int =
      x.surname.compareTo(y.surname)
  }
def listPeople(persons: Seq[Person])
              (using ordering: Ordering[Person]) = persons.sorted(ordering)

Utilisation :

val people = List(Person("Weasley", "Ron", 15), Person("Potter", "Harry", 15)) 
listPeople(people) // <- le compilateur injecte l'ordering ici

3.2 Implicit resolution

Lorsque le compilateur voit un appel de méthode où un paramètre using est manquant, comme dans listPeople(people), il va utiliser un algorithme pour rechercher les instances given correspondantes. C’est le mécanisme implicit resolution.

Pour un paramètre using t: T, le compilateur va rechercher un given de type T dans cet ordre :

  • portée locale : dans le même bloc ou méthode
  • import explicite : import Person.defaultPersonOrdering
  • import avec joker : import Person.*
  • companion object : l’objet companion de T et les companions de ses paramètres de type
    • pour Ordering[Person], recherche dans l’object Ordering ET dans Person.
  • les super-classes de T et les classes englobant T (lorsque T est une classe interne).
Note

Les mots-clé given et using ont été introduits dans Scala 3. Vous pouvez parfois tomber sur des API écrites en Scala 2 qui utilisent le mot-clé implicit. Voici l’équivalence :

Scala 3.x Scala 2.x
given ord: Ordering[Person] = ??? implicit val ord: Ordering[Person] = ???
def tri[A](seq: Seq[A])(using ord: Ordering[A]) = ??? def tri[A](seq: Seq[A])(implicit ord: Ordering[A]) = ???

3.3 Dérivation de given

Nous pouvons déclarer des méthodes avec given. Cela va permettre au compilateur de construire des instances à la volée.

Par exemple, supposons que :

  • notre code métier a besoin de comparer des Option[Person], puis des Option[Product].
  • nous avons défini un given Ordering[Person] et un given Ordering[Product].

Cela ne suffit pas ! Il faudrait aussi déclarer :

  • given Ordering[Option[Person]] et
  • given Ordering[Option[Product]].

Nous pouvons déclarer un seul given de la manière suivante :

given optionOrdering[T](using ord: Ordering[T]): Ordering[Option[T]] with
  def compare(optA: Option[T], optB: Option[T]): Int = 
    (optA, optB) match 
      case (None, None) => 0
      case (None, _) => -1
      case (_, None) => 1
      case (Some(a), Some(b)) => ord.compare(a, b)

Cette définition indique au compilateur :

  • “si tu as une instance given Ordering[T],
  • tu peux automatiquement créer une instance given Ordering[Option[T]] en appelant la méthode optionOrdering.

Ce mécanisme est très puissant, car le compilateur peut enchaîner plusieurs appels en cascade. On peut ainsi obtenir un Ordering[Option[Option[T]] sans code supplémentaire. C’est particulièrement utile pour encoder/décoder des données dans un format.

Autre exemple : nous souhaitons pouvoir afficher des Double, ou des List[Double], ou des List[List[Double]], ou des Option[List[Option[Double]]] dans un format particulier :

Définitions :

trait Show[A]:
  def show(a: A): String

object Show:
  // Show avec 2 chiffres décimaux
  given Show[Double] with
    def show(a: Double): String = f"$a%6.2f"

  // Si on connaît Show[A], on sait construire Show[List[A]]
  given [A](using showA: Show[A]): Show[List[A]] with
    def show(list: List[A]): String =
      list.map(showA.show).mkString("[", ", ", "]")

  // Si on connaît Show[A], on sait construire Show[Option[A]]
  given [A](using showA: Show[A]): Show[Option[A]] with
    def show(opt: Option[A]): String = opt match
      case Some(a) => showA.show(a)
      case None => "None"

Utilisation :

def display[A](value: A)(using s: Show[A]): Unit =
  println(s.show(value))

display(List(1.234, 2000, 3))
// [  1.23, 2000.00,   3.00]
display(List(List(1.234, 2), List(3, 4.1), List(5.0)))
// [[  1.23,   2.00], [  3.00,   4.10], [  5.00]]
display(Option(List(Some(1.234), Some(3.3), None)))
// [  1.23,   3.30, None]

4 Méthodes d’extension

Une méthode d’extension permet d’ajouter une méthode à un type sans le modifier. Par exemple, imaginons que nous utilisons une bibliothèque externe qui définit :

case class Circle(x: Double, y: Double, radius: Double)

Cette classe ne possède pas de méthode area, et nous ne pouvons pas modifier son code. Nous pouvons simplement créer un nouvel objet :

object CircleHelpers:
  def area(c: Circle): Double = 
    math.Pi * c.radius * c.radius

Cependant, elle n’est pas pratique à utiliser :

val c = Circle(2, 3, 4)
val a = CircleHelpers.area(c)

Nous aurions aimé pouvoir utiliser c.area, comme si la méthode était définie dans Circle. C’est possible avec les méthodes d’extension. Au lieu de définir un object, nous définissons une extension :

package object lib:

extension (c: Circle)
  def area: Double = c.radius * math.Pi * 2

Avec un import, on peut ensuite utiliser area comme une méthode :

import lib.area

val c = Circle(2, 3, 4)
val a = c.area

5 Classes de type (type classes)

  • En POO, une classe permet de définir des comportements communs à plusieurs objets.
    • une classe Animal définit des méthodes manger(), dormir() que tous ses objets peuvent utiliser.
    • les objets sont des instances de classes
  • En Programmation Fonctionnelle, une classe de type permet de définir des comportements communs à plusieurs types.
    • Une classe de type définit des fonctions show(), compare que tous les types qui l’implémentent doivent fournir.
    • pour chaque type, nous aurons une instance de la classe de type

Pour définir une classe de type En Scala, nous devons :

  1. Définir une interface trait possédant un paramètre de type
  2. Définir les instances given de ce trait pour chaque type souhaité.
  3. (optionnel) ajouter des méthodes d’extension pour simplifier la syntaxe pour les appelants.

Le concept permet de faire implémenter une interface à des types sans avoir à les modifier. On parle d’ad-hoc polymorphism : on peut changer la forme de notre objet à la volée, juste en changeant des imports.

5.1 Classe de type : JsonSerializer

Voici un exemple de classe de type qui permet de convertir un objet en Json :

// 1. Type class definition
trait JsonSerializer[A]:
  def toJson(value: A): String

// 2. Instances for different types
object JsonSerializer:
  
  given JsonSerializer[Int] with
    def toJson(value: Int): String = value.toString
  
  given JsonSerializer[String] with
    def toJson(value: String): String = s""""$value""""
  
  given JsonSerializer[Boolean] with
    def toJson(value: Boolean): String = value.toString
  
  given [A](using serializer: JsonSerializer[A]): JsonSerializer[List[A]] with
    def toJson(values: List[A]): String =
      values.map(serializer.toJson).mkString("[", ", ", "]")

// 3. Extension method
extension [A](value: A)(using s: JsonSerializer[A])
  def toJson: String = s.toJson(value)

Avec ces définitions, lorsqu’on appelle .toJson sur un objet de type T, le compilateur va rechercher une instance given de type JsonSerializer[T] dans le scope.

// Utilisation
42.toJson             // 42
"hello".toJson        // "hello"
true.toJson           // true
List(1, 2, 3).toJson  // [1, 2, 3]
List("a", "b").toJson // ["a", "b"]

La flexibilité de cette approche est remarquable. Une bibliothèque JSON peut proposer des instances pour les types standards, que vous pouvez étendre facilement pour vos propres types :

case class Person(name: String, age: Int)

given JsonSerializer[Person] with
  def toJson(p: Person): String =
    s"""{"name": "${p.name}", "age": ${p.age}}"""

List(Person("Alice", 30), Person("Bob", 20)).toJson  
// [{"name": "Alice", "age": 30}, {"name": "Bob", "age": 20}]

Tout est validé à la compilation. L’appel à .toJson ne compilera pas si les instances de type class du bon type ne sont pas déclarées.

5.2 Classes de types dans les bibliothèques

Le SDK Scala propose quelques classes de type :

  • scala.math.Ordering pour trier et comparer
  • scala.math.Numeric pour les opérations arithmétiques +, -, *, …
  • scala.CanEqual permet d’avoir une erreur de compilation lorsqu’on compare 2 types différents avec == (voir TP).

La bibliothèque Cats définit plusieurs classes de types provenant de la théorie des cagégories. Cette théorie mathématique étudie les structures et leurs relations, et a des connexions avec la programmation fonctionnelle. Il n’est heureusement pas nécéssaire de comprendre cette théorie pour utiliser les principales classes de types de Cats.

5.2.1 cats.Functor

Un Functor est un type sur lequel on a l’opération map :

trait Functor[F[_]] {
  def map[A, B](fa: F[A])(f: A => B): F[B]
}

Nous avons vu que plusieurs types du SDK implémentaient map, comme Option, Either, Seq, … L’avantage du type Functor est que nous pouvons définir des méthodes qui s’appliquent à tous ces types.

Cela permet de renforcer le principle of least power : si la seule chose dont j’ai besoin dans mon paramètre est la fonction map, je peux le déclarer comme Functor.

import cats._
import cats.syntax.all._
import cats.instances.all._

// Méthode générique - fonctionne avec TOUT Functor
def applyDiscount[F[_]](prices: F[Double], 
                        discount: Double)(using Functor[F]): F[Double] =
  prices.map(_ * (1 - discount))

// Tous ces exemples fonctionnent sans définir d'instances !
val optPrice: Option[Double] = Some(100.0)
val opt = applyDiscount(optPrice, 0.2)
// Some(80.0)

val listPrices = List(100.0, 200.0, 300.0)
val lst = applyDiscount(listPrices, 0.2)
// List(80.0, 160.0, 240.0)

val eitherPrice: Either[String, Double] = Right(100.0)
val eith = applyDiscount(eitherPrice, 0.2)
// Right(80.0)

import scala.concurrent.Future
import scala.concurrent.ExecutionContext.Implicits.global

val futurePrice = Future { Thread.sleep(10); 100.0 }
val fut = applyDiscount(futurePrice, 0.2)
// Future(80.0)
Note

Scala offre un sucre syntaxique pour les fonctions qui utilisent une classe de type. Au lieu de déclarer :

def applyDiscount[F[_]](prices: F[Double], 
                        discount: Double)(using Functor[F]): F[Double] = ???

Nous pouvons déclarer Functor derrière le paramètre de type :

def applyDiscount[F[_] : Functor](prices: F[Double], 
                                  discount: Double): F[Double] = ???

Cette syntaxe reflète bien l’analogie entre objets/classes et types/classes de types :

dog: Dog      // objet dog, classe Dog
F[_]: Functor // type F[_], classe de type Functor

5.2.2 cats.Monad

From A Brief, Incomplete, and Mostly Wrong History of Programming Languages “a monad is a monoid in the category of endofunctors, what’s the problem?”

La classe de type Monad a des “pouvoirs” en plus par rapport à Functor : elle permet d’aplatir (flatten) des structures, et de construire (pure) une structure à partir d’une valeur. Comme elle dérive de Functor, elle implémente également flatMap, qui est une combinaison de map et flatten.

Une définition simplifiée de la classe de type Monad ressemblerait à ceci :

trait Monad[F[_]] extends Functor[F] {
  // construit un F avec une valeur
  def pure[A](x: A): F[A]

  // la méthode clé qui caractérise une structure monadique 
  def flatMap[A, B](fa: F[A])(f: A => F[B]): F[B]

  // flatten peut être implémenté avec flatMap
  def flatten[A](ffa: F[F[A]]): F[A] =
    flatMap(ffa)(fa => fa)
}

La méthode flatMap est fondamentale : elle permet de chaîner des opérations qui produisent elles-mêmes des Monads. Cela permet d’enchaîner des traitements les uns à la suite des autres dans un contexte donné. Un Monad représente en quelque sorte un contexte de calcul avec des capacités spécifiques :

  • Option => contexte “ce calcul peut ne pas renvoyer de valeur”
  • Either => contexte “ce calcul peut échouer avec une erreur typée”
  • Future => contexte “ce calcul est asynchrone/effectue des effets de bord”
  • cats.IO => contexte “ce calcul a des effets de bord”
  • Writer => contexte “ce calcul produit des logs en plus de sa valeur”
  • State => contexte “ce calcul peut lire/modifier un état”

Nous avions vu que for en Scala était du sucre syntaxique permettant d’enchaîner des flatMap et map. Cela signifie que nous pouvons utiliser for sur tous les types monadiques !

Cats fournit :

  • des instances de Monad pour les types courants du SDK comme Option, List, Either, …
  • d’autres types monadiques, comme IO, State, NonEmptyList, Writer…
  • des “Monad transformers”, qui permettent de combiner plusieurs Monads

Exemple utilisant Writer[L, A], qui permet de logger des informations :

import cats.data.Writer
import cats.syntax.all._

// type alias: évite de répéter Writer[...] partout
type Logged[A] = Writer[List[String], A]

def validateUser(name: String): Logged[Boolean] =
  if name.isEmpty then
    Writer(List("Validation: Name is empty"), false)
  else
    Writer(List(s"Validation: Name '$name' is valid"), true)

def saveToDatabase(name: String): Logged[Int] =
  Writer(List(s"Database: Saved user '$name'"), name.hashCode)

def sendEmail(userId: Int): Logged[Unit] =
  Writer(List(s"Email: Sent welcome email to user $userId"), ())

// For-comprehension avec Writer
def registerUser(name: String): Logged[Option[Int]] =
  for {
    isValid <- validateUser(name)
    result  <- if isValid then
                 for {
                   userId <- saveToDatabase(name)
                   _      <- sendEmail(userId)  // _ pour ignorer Unit
                 } yield Some(userId)
               else
                 Writer(List[String](), None)
  } yield result

val (logs, result) = registerUser("Alice").run
logs.foreach(println)
// Validation: Name 'Alice' is valid
// Database: Saved user 'Alice'
// Email: Sent welcome email to user 63679911

println(s"Result: User ID = $result")
// Result: User ID = Some(63679911)
